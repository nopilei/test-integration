# Интеграция с risk-провайдером

Стек: FastAPI · SQLAlchemy 2.0 async · PostgreSQL · RabbitMQ · FastStream ·
Alembic · aiohttp · prometheus-client.

## Допущения по дизайну

1. Не прописан протокол общения с провайдером -> Описан свой формат сообщений, добавлен тип сообщения для 
ответа провайдера, ключ идемпотентности message_id, все остальное замокано. Также предполагается, что 1 фрейм относится к
1 тикету.
2. Не ясно отношение между интеграцией и монолитом, к которому надо обращаться после ответа провайдера -> Сделано
предположение что это отдельный сервис, общение с ним замокано
3. Статусы тикетов не описаны -> Придумал свои
4. Не ясно что делать с тикетами которые застряли в промежуточном статусе -> Шлем REQUEST_CANCELLATION провайдеру, таймаут выбрал сам
5. Не известна пропускная способность провайдера -> Сделано допущение что стоит читать из очереди и отправлять по одному сообщению за раз
6. То же самое про монолит -> Читаем по одному и пишем по одному, без батчинга

# Описание системы

1. Получаем запрос на создание тикета по API (FastAPI)
2. Сохраняем в бд (сам тикет + outbox)
3. Воркер (outbox_producer) стучится в таблицу outbox и пишет в RabbitMQ очередь (provider.out)
4. Воркер (provider_gateway) читает из очереди и отправляет по вебсокету провайдеру сообщение на создание тикета, и
   конкурентно читает из вебсокет и пишет в очередь (provider.in). Сообщения проходят через 3 ретрая при неуспехах 
   и потом попадают в DLQ.
5. Воркер (provider_consumer) читает из очереди provider.in и стучится в монолит и меняет статусы,
   создает записи outbox если надо отправить ответ провайдеру.
6. Воркер (reconciler) стягивает тикеты которые застряли в промежуточных статусах из-за ошибок и шлет запросы 
   провайдеру на отмену

# Что реализовано

Логика интеграции с провайдером:  Создание тикета по апи, отправка сообщения провайдеру, получение ответов, отправка 
запроса в локальный сервис (монолит). Сделан упор на отказоустойчивость, консистентность, гарантии доставки (
идемпотентное создание тикетов, аутбокс, ретраи)

# Что не реализовано

Управление реальным конекшеном по вебсокету заменен на мок, также и с вызовами в монолит. Можно задать вероятность 
возникновения исключений при использовании замоканых клиентов, чтобы проще протыкать локально.



### Процессы
У каждого процесса есть Kubernetes-подобные probes: `/health/live`,
`/health/ready`, `/health/startup` и метрики Prometheus на `/metrics`.

### Стейт-машина тикета

```
   NEW → SENT_TO_PROVIDER → RECOMMENDED_CONFIRM ┐
                          → RECOMMENDED_DECLINE ┤→ SETTLED → CONFIRMED | DECLINED

   любой нетерминальный ─ (локальный сбой, таймаут reconciler, конфликт монолита)
                    ↓
             CANCELLATION_REQUESTED → CANCELLED
```
## Быстрый старт

```bash
cp .env.example .env
docker compose up --build
```

Эндпоинты:
* API — <http://localhost:8000>
* RabbitMQ management UI — <http://localhost:15672> (guest/guest)
* Probes/metrics воркеров — `:8081`, `:8082`, `:8083`

### Создать тикет

```bash
curl -i -X POST http://localhost:8000/api/v1/tickets \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: super-secret-api-key' \
  -H 'Idempotency-Key: 8b0e01d2-2ff0-4dcb-8f9a-7f0c1b5c1a10' \
  -d '{
    "user_id": "0f7d1a3c-1a8e-4a3d-8ea9-8b0e01d20000",
    "stake_amount": "500.00",
    "currency": "RUB",
    "selections": [
      {"event_id": "match:atp:2024-06-01:djokovic-medvedev", "market": "1x2", "odds": "1.85"}
    ]
  }'
```

Ответ `202 Accepted`:

```json
{
  "ticket_id": "…",
  "status": "new",
  "created_at": "…"
}
```
